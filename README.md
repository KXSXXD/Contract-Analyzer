# Contract Risk Analyzer

Upload a contract → clauses are segmented, classified by type, and scored for
risk by comparing wording against a corpus of standard/fair reference clauses
plus rule-based red-flag detection.

## Why this architecture (the story to tell an examiner)

The lazy version of this project is "call an LLM API and print whatever it
says." That's not defensible in a viva — you can't explain *why* it flagged
something, and it's not really "your" system. This build avoids that by
splitting the problem into four independent, inspectable stages:

```
Raw contract text
      │
      ▼
[1] extraction.py   — heuristic clause segmentation (numbered headings /
      │                paragraph breaks). No ML needed here; this is a
      │                structural parsing problem, not a language problem.
      ▼
[2] classifier.py   — TF-IDF + Logistic Regression, trained on a hand-
      │                labeled corpus (data/training_data.py) of 15 clause
      │                types (indemnity, termination, liability, IP,
      │                confidentiality, non-compete, etc). This is the
      │                actual "trained an NLP model" piece.
      ▼
[3] risk_engine.py  — TWO independent, explainable signals per clause:
      │                 (a) cosine similarity (TF-IDF) between the clause
      │                     and the nearest "standard/fair" reference
      │                     clause of the same type — low similarity =
      │                     unusual phrasing = higher risk.
      │                 (b) rule-based red-flag phrase matching (e.g.
      │                     "sole discretion", "in perpetuity", "no cap
      │                     of any kind") with severity weights.
      │                These combine into a 0-100 risk score with a
      │                human-readable reason for every flag.
      ▼
[4] FastAPI (main.py) exposes /analyze; a single-file HTML/JS frontend
    renders per-clause risk + an overall contract risk score.
```

This gives you a genuine technical story for the viva: *"I trained a
15-class clause classifier and evaluated it with stratified k-fold
cross-validation (see the printed report), then built a separate,
explainable risk-scoring layer that doesn't depend on the classifier being
right — even a misclassified clause still gets checked against the global
red-flag rules."* That's a much stronger answer than "I called GPT."

### Honest limitations (say these before the examiner does)
- The classifier is trained on **63 hand-labeled examples across 15
  classes** — cross-validated accuracy is ~65%, which is fine for a demo
  but is explicitly a "small labeled dataset" limitation. The natural
  extension is scraping/labeling real (de-identified) contract clauses to
  grow `data/training_data.py`, or swapping in a transformer sentence
  encoder in `classifier.py` without touching the rest of the pipeline.
- Clause segmentation is heuristic (regex on numbering/paragraphs), not
  learned. That's a deliberate, defensible choice — it's a structural
  problem, not one that benefits from ML — but say so proactively.
- Risk scoring is a **rule-based + similarity hybrid**, not a trained risk
  classifier. This is intentional (explainability > opacity for a legal
  tool) but be ready to say why you chose it that way.

## Project structure

```
contract-risk-analyzer/
├── backend/
│   ├── app/
│   │   ├── main.py          FastAPI app, /analyze and /analyze-text endpoints
│   │   ├── extraction.py    clause segmentation
│   │   ├── classifier.py    loads trained model, predicts clause type
│   │   ├── risk_engine.py   similarity + red-flag risk scoring
│   │   ├── file_reader.py   .txt / .pdf / .docx text extraction
│   │   └── schemas.py       pydantic response models
│   ├── data/
│   │   ├── training_data.py   63 labeled example clauses (15 categories)
│   │   ├── clause_corpus.json standard/fair reference clauses per category
│   │   └── red_flags.json     global + per-category red-flag phrase rules
│   ├── sample_contracts/
│   │   ├── sample_contract_risky.txt      (scores ~76/100, High)
│   │   └── sample_contract_standard.txt   (scores ~19/100, Low)
│   ├── train_classifier.py  trains + cross-validates + saves the model
│   ├── model/clause_classifier.joblib     (generated by training)
│   └── requirements.txt
└── frontend/
    └── index.html          single-file demo UI (no build step)
```

## Setup

```bash
cd backend
pip install -r requirements.txt
python train_classifier.py        # trains and saves the model, prints CV report
uvicorn app.main:app --reload --port 8000
```

Then open `frontend/index.html` in a browser (serve it locally, e.g.
`python -m http.server 5500` from the `frontend/` folder, rather than
opening via `file://`, so the sample-loading buttons can fetch the sample
files). Click **"Load risky sample"** or **"Load standard sample"**, or
paste/upload your own contract, then **Analyze Contract**.

API docs (Swagger) are auto-generated at `http://127.0.0.1:8000/docs`.

## Demo script for your viva

1. Load the **standard sample** → show overall score ~19 (Low), most
   clauses green.
2. Load the **risky sample** → show overall score ~76 (High), point at 2-3
   specific clauses (e.g. Limitation of Liability, Payment Terms) and read
   out the red-flag explanations — "no limitation or cap of any kind",
   "Company reserves the right to unilaterally increase fees."
3. Open `/docs` and show the classifier's cross-validated report from
   `train_classifier.py` output — this is your "I evaluated my model"
   evidence.
4. Explain the architecture diagram above: segmentation → classification →
   two-signal risk scoring → API → UI.
5. If asked "how would you improve this": more labeled training data, a
   transformer-based encoder (e.g. sentence embeddings) swapped into
   `classifier.py`, a real contract corpus (CUAD dataset is a well-known
   public one) instead of hand-written examples, and persistent storage
   for uploaded/analyzed contracts.

## Extending it further (optional, if you have time before submission)
- Swap TF-IDF clause classification for the public **CUAD** (Contract
  Understanding Atticus Dataset) to get thousands of real labeled clauses
  instead of 63 hand-written ones — this is the single highest-leverage
  improvement and a great thing to mention as "future work" even if you
  don't have time to integrate it.
- Add a PDF report export (risk summary + flagged clauses) — pairs well
  with the `pdf` generation skill if you're building this further with
  Claude.
- Add user accounts + contract history using a simple SQLite database.
